Matching Engine Journal & Replay · Knowledge notes

Durability { Append & flush }

A journal is only useful if records that “succeeded” can be found after a crash. That is an I/O and flush-policy problem, not a matching problem.

01

Why append-only

Trading journals almost never update middle bytes. You append new records. Benefits:

  • Simple recovery — scan from start (or from a snapshot offset later).
  • Crash-friendly — the only dangerous region is the tail (last partial write).
  • Audit-friendly — history is immutable once written.
Invariant

Never rewrite an earlier record in place in v1. If you need a correction, append a compensating command (or start a new journal) — do not patch history.

02

Live write path

journal_run (conceptual)
for each command in scenario:
  1. apply to MatchingEngine          // match first or journal first?
  2. encode(command) → bytes
  3. write(bytes) to file
  4. optional fsync
  5. collect live events for goldens

Match-then-journal vs journal-then-match

OrderIf crash between stepsv1 lean
Match → journal Book advanced but record missing → replay understates state Acceptable for offline scenario runner; document it
Journal → match Record present but match never ran → replay may “invent” progress vs last live view Closer to durable-intent systems
v1 teaching choice

For a scenario CLI (not a live exchange), match then append is fine and easier to test: you only journal commands you successfully applied. Say this out loud in interviews — production order servers often journal (or replicate) before acknowledging the client.

03

fsync policy

write / fwrite usually copies into the kernel page cache. A process crash may still leave data in the cache; a machine power loss may not. fsync(fd) (or fdatasync) asks the OS to push file data to stable storage.

PolicyDurabilityThroughput
Never fsync (rely on OS) Weak across power loss Highest
fsync every record Strongest per command Slow (disk latency per order)
fsync every N records / batch Bounded loss window Middle
fsync on close / CLI end Good for offline scenario runs Fine for demos
Decision lean

Ship a flag: default fsync on close (and optionally every record for demos). Measure / discuss the trade-off; do not hard-code “always sync” without noting cost.

04

Crash models (what you claim)

FailureWhat you guarantee in v1
Clean exit after close/fsync Full journal readable; replay = last live book
Kill −9 mid-run Prefix of complete records OK; last partial record detected via trunc/CRC and rejected
Power loss without fsync May lose trailing records still in page cache — be honest
Bit flip in middle of file CRC mismatch → fail closed at that record

Replay must never “guess” past a bad tail. Better to stop and report than to desync the book.

mmap for read Fast large-file scan Out of v1; extra pitfalls
Writer sketch
class JournalWriter {
public:
  explicit JournalWriter(const std::filesystem::path& path,
                         bool fsync_each = false);
  void append(const Command& cmd);  // encode + write + optional fsync
  void sync();                     // explicit fsync
  ~JournalWriter();                // flush + close (+ sync if policy)
};
06

RAII for file handles

Same lesson as MDS SocketGuard: if you own an int fd, close it in the destructor; delete copy; allow move. Do not leave bare fds in main.

  • Open with create/truncate for journal_run (new run file).
  • Open read-only for journal_replay.
  • Write header once on create; append records after.
07

Project decision

Decision

Append-only binary file via a small JournalWriter / JournalReader RAII pair. Default durability: flush on close; optional per-record fsync. Match-then-journal for the scenario CLI. Rejected: rewriting mid-file, mmap in v1, pretending power-loss safety without sync.

08

Common pitfalls

✕

Calling it “durable” after write alone

Page cache ≠ disk. Interviewers love this distinction.

✕

Opening the journal in text mode

On some platforms text mode rewrites newlines. Always binary.

✕

Buffering incomplete records across process restart

In-memory buffers die with the process. Only complete on-disk records count after recovery.
