Matching Engine Journal & Replay · Knowledge notes

Integrity { Detect bad tails }

A journal without integrity checks will silently mis-parse a truncated or flipped last record and rebuild the wrong book. Checksums turn that into a loud, testable failure.

01

Why checksums

Two common bad endings after a crash or bad copy:

  1. Truncation — file ends mid-record (partial write).
  2. Corruption — full-length record, wrong bytes (bit flip, bad edit).

Length alone catches (1) if you know the expected size. A CRC catches (2) and many truncated cases where leftover bytes look like a plausible short record.

Demo value

Corrupt the last few bytes of a good .jnl → replay exits with a clear checksum/truncation error. That is a portfolio-ready story.

02

CRC32 (enough for v1)

CRC32 is a fast, well-known integrity polynomial checksum — not cryptography. It detects accidental corruption; it does not stop a motivated attacker who can recompute the CRC.

ToolUse here?
CRC32 Yes — per-record trailer
Running hash of whole file Optional extra; not required if per-record is solid
SHA-256 / HMAC Overkill for learning; auth is out of scope

Implement a small table-driven CRC32 (or use a well-known snippet you understand). Document the polynomial (e.g. ISO Ethernet CRC-32). Unit-test against a known vector (“123456789” → classic check value).

03

What bytes enter the CRC

coverage
crc32( type ‖ body )   →  store as u32 LE trailer

Do NOT include the CRC bytes in the CRC input.
File header: either unprotected metadata, or its own checksum field.

On write: compute CRC → append trailer. On read: recompute over type‖body → compare to trailer (constant-time compare not required for this threat model).

04

Truncated tails

Reader has remaining bytes at EOF:

SituationAction
remaining == 0 after last good record Clean end — success
0 < remaining < full record size Truncated — error (do not apply partial)
Full size but CRC mismatch Corrupt — error
Prefix salvage (optional story)

Production systems sometimes replay all good prefix records and discard the bad tail. v1 can simply fail the whole replay when any bad record appears — simpler tests. Mention salvage as a later improvement.

05

Corruption mid-file

If record k fails CRC, later records are untrustworthy even if their CRCs pass (you may be desynced on framing). Fail at first error.

Unknown type byte: also fail closed — do not skip. Skipping would desync fixed framing.

06

Fail-closed policy

  • Bad magic / version in header → refuse.
  • Bad type / CRC / trunc → refuse (non-zero exit).
  • Never invent defaults for missing fields.
reader outcome
enum class JournalError {
  Ok,
  BadMagic,
  UnsupportedVersion,
  TruncatedRecord,
  BadChecksum,
  BadType,
  IoFailure,
};
07

Implementation notes

  • Put CRC helpers in include/crc32.hpp (or inside journal_record.hpp).
  • Unit-test: encode → flip one payload byte → decode reports BadChecksum.
  • Unit-test: drop last 3 bytes of file → TruncatedRecord.
  • Keep CRC in the record trailer little-endian, same as other multi-byte fields.
08

Project decision

Decision

Per-record CRC32 over type‖body; fail-closed on trunc, bad CRC, or unknown type. Not crypto. Rejected: unsigned plaintext journals, silent skip of bad tails in v1.
