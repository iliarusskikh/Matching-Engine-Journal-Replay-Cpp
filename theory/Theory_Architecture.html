Matching Engine Journal & Replay · Knowledge notes

Architecture { Persist & rebuild }

What this repo owns: an append-only command log around a vendored LOB, plus a replay path that rebuilds book state bit-identical to a live run. Networking and concurrency stay in the other projects.

01

Purpose

The LOB already matches correctly in RAM. The gateway already fans orders across threads. Neither answers: after a crash or cold start, how do we get the same book back?

This project adds the missing slice: serialize → append → replay → prove identical.

Core idea

Log every accepted input (NEW / CANCEL). Replay feeds those commands into a fresh MatchingEngine. Deterministic matching ⇒ same trades and same resting book.

02

Live path & replay path

v1 data paths
LIVE (journal_run)
  scenario.txt
       │
       ▼
  parse NEW / CANCEL ──► MatchingEngine::submit / cancel
       │                        │
       │                        ▼
       │                   live events / L2 checks
       ▼
  JournalWriter.append(command) ──► run.jnl  (append-only)

REPLAY (journal_replay)
  run.jnl
       │
       ▼
  JournalReader (verify CRC) ──► MatchingEngine (fresh)
       │
       ▼
  rebuilt events / book  ==  live goldens

Two CLIs, one format. The writer never needs the reader’s state machine; the reader never mutates an existing engine mid-flight — always start empty and rematch from byte 0 (v1).

03

Command journal (not event journal)

DesignLogsReplay meansv1?
A — Command Inputs: NEW, CANCEL Drive MatchingEngine again Yes
B — Event Outputs: ACCEPT / TRADE / CANCEL Audit stream, or rebuild book from events with extra rules Later optional

Command journaling is enough when matching is deterministic: same ordered inputs ⇒ same outputs. You do not store trades on disk; you recompute them. That mirrors LOB scenario goldens and keeps the on-disk schema small.

Assumption you must keep true

No hidden non-determinism in the vendored LOB (no wall-clock in match decisions, no random tie-breaks). Replay identity tests will catch regressions.

Locked decisions (v1)

TopicChoiceWhy
Payload Commands only Small; rematch; pairs with LOB goldens
Format Binary packed records + per-record checksum Same discipline as MDS; portable
Threads Single-threaded Persistence lesson without queue noise

07

Rejected alternatives

✕

Text / JSON journal

Fine for demos; weak on CV for binary I/O and integrity. Prefer packed records + CRC so trunc/corrupt tests are meaningful.

✕

Event-only log as v1 recovery

Useful for audit of published outputs, but rebuilding the book from events needs extra rules. Rematch from commands is the cleaner recovery story.

✕

Embedded SQLite / Raft / multi-node

Wrong lesson for a fourth bullet. One process, one file, correct rebuild.

✕

Rewriting the LOB in this repo

Matching rules already live in the LOB project. Vendor a slim core; spend engineering on journal + replay.

08

Implement order (shipped)

  1. Vendor LOB + scenario load.
  2. Record layout + CRC encode/decode unit tests.
  3. JournalWriter + journal_run.
  4. JournalReader + journal_replay.
  5. Identity goldens + trunc/corrupt negatives.
  6. Optional polish: docs; --fsync-each already on the CLI.
