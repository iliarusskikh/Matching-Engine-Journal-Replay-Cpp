Matching Engine Journal & Replay · Knowledge notes

Replay { Rebuild from the log }

Recovery is not “reload RAM.” It is: open the journal, verify records, feed a fresh engine in order, and obtain the same book and event stream you would have gotten live.

01

What “recovered” means

After replay succeeds:

  • Resting book (bids/asks, quantities, order ids) matches the live run.
  • Emitted event sequence matches (ACCEPT / TRADE / CANCEL lines), ignoring wall-clock timestamps if any.
  • Any L2 / CHECK_BEST_* style assertions that passed live also pass on the rebuilt engine.
Market meaning

Audit trail + crash recovery + research replay (“re-run Friday’s tape offline”) — all the same mechanism when the log is commands and matching is deterministic.

02

Replay algorithm (v1)

journal_replay
1. open path read-only
2. read + validate file header (magic, version)
3. engine = MatchingEngine{}          // empty
4. while true:
     status = read_next_record(cmd)
     if Done: break
     if Truncated|BadChecksum|BadType: fail exit
     apply(engine, cmd)               // submit or cancel
     append events to replay_log
5. print book / events / run checks
6. success exit

Apply order must match the order commands were journaled — FIFO by file offset. No parallel apply in v1.

03

Determinism contract

Command journaling only works if:

RequiredForbidden in match path
Same inputs in same order Wall-clock affecting match decisions
Same LOB version / rules Randomized FIFO tie-breaks
Same numeric types / scaling Reading “current” external state mid-match

Your vendored LOB already aims at this (golden scenarios). Replay tests are a second line of defense: if someone “improves” matching with a non-deterministic detail, identity tests fail.

04

Proving live ≡ replay

  1. Run scenario through engine without journal → capture event vector / book snapshot A.
  2. Run same scenario with journaling → capture live B (should equal A) and file F.
  3. Replay F → capture C.
  4. Assert A == B == C (events + book).

In tests you can skip the CLI and call writer/reader APIs directly for speed.

05

Idempotency (know the word)

If a writer retries after an uncertain write, you might append the same command twice. Replay would then apply it twice — usually wrong.

  • v1 scenario runner: single-threaded, no retry layer → low risk.
  • Interview follow-up: sequence numbers per record, or “write once then fsync,” or detect dup ids.
v1 scope

Do not build a full exactly-once protocol. Understand the hazard; keep the writer simple and crash tests focused on trunc/CRC.

06

Snapshots (optional later)

Genesis replay is O(n) in journal length. Later:

  • Periodically serialize book snapshot + byte offset into the journal.
  • Recovery: load snapshot, then replay only the suffix.

Out of v1 on purpose — prove correctness from byte 0 first.

07

CLI shape (target)

commands
./journal_run scenarios/demo.txt -o run.jnl [--fsync-each]
./journal_replay run.jnl
# exit 0 → print events / best bid-ask
# exit ≠ 0 → integrity or I/O error on stderr
08

Project decision

Decision

Ordered command rematch from genesis into a fresh engine. Identity with live run is the acceptance test. Snapshots, mmap, and event-journal mode are optional later. Rejected: rebuilding book from TRADE events as the v1 recovery path.
